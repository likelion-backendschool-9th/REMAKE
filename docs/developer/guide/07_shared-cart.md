## 구현 메모

### ERD와 맞춰야 하는 장바구니 계약(#57)

- 식단표에서 담아도 원본 `recipe_id`를 저장해요. nullable `meal_plan_slot_id`는 최초 담기 출처이며, 기존 항목을 재사용해도 다른 칸 번호로 덮어쓰지 않아요. `meal_plan_id`·`group_name`은 복원하지 않아요. 컬럼 정의는 [ERD 19번](../erd.md#19-cart_items-장바구니)을 기준으로 보세요.
- 식단 칸 행이 삭제되면 슬롯 FK는 `ON DELETE SET NULL`로 비워지고 원본 레시피는 남아요. 다만 칸 삭제·교체·덮어쓰기는 칸을 지우거나 바꾸기 전에 그 칸에서 담은 장바구니 행을 먼저 정리해요(아래 #91 줄). 내·공유 레시피 저장 취소는 장바구니와 독립적으로 처리하고, 장바구니 행과 사용자 수정 수량을 유지해요.
- 담기 중복은 사용자+원본 recipeId+정확히 일치하는 재료명+단위로 판단해요. 저장 취소 후 새로 저장하면 현재 부족한 재료 중 해당 레시피 장바구니에 없는 재료만 추가해요. 기존 행과 수량은 유지해요. 이미 저장된 PUT의 재시도는 멱등성을 유지하며 새 담기를 실행하지 않아요.
- 한 번의 식단 생성에서 같은 원본 레시피를 여러 끼니에 쓰면 이번 생성분의 같은 레시피·재료명·단위별 부족 수량을 먼저 합산해요. 생성 전부터 있던 장바구니 항목에는 누적하지 않아요. `cartAddedCount`와 E62의 개수는 실제 추가 행 수예요.

## 공유 레시피 저장·취소 (#90)

- API 53 `PUT /api/v1/user/shared-recipes/{id}/save`는 `200 { saveCount, saved, cartAddedCount }`, API 54 `DELETE /api/v1/user/shared-recipes/{id}/save`는 `200 { saveCount, saved }`를 반환해요. 두 API 모두 로그인과 공개 게시글 확인이 필요해요. 없는 글·숨긴 글은 `SHARED_RECIPE_NOT_FOUND`예요.
- `share` 영역은 `SaveSharedRecipeReferenceUseCase`를 통해 `recipe` 영역의 저장을 변경해요. 원본 `recipe_id`와 저장 출처 `shared_recipe_id`를 연결하고 레시피·재료·단계 사본을 만들지 않아요. 저장 수는 해당 게시글을 출처로 가진 현재 `saved_recipes` 행 수예요.
- 같은 사용자의 같은 원본은 한 번만 저장해요. 다른 주 게시글이나 내 저장 목록에서 이미 저장한 원본도 출처·즐겨찾기·저장 시각을 바꾸지 않아요. 이미 저장한 PUT에서는 장바구니 담기와 E44를 다시 실행하지 않아요.
- 부족 재료는 공유 상세와 같이 요청자의 소비기한이 지나지 않은 냉장고 재료명으로 판단해요. 작성자의 `ingredientId`나 수량은 보유 판정에 쓰지 않아요. 공통 담기가 물·수량 없는 재료·PINCH·TO_TASTE를 제외해요. **기본 양념(소금·식용유·후추·설탕)도 냉장고에 없으면 부족**입니다(관리 목록, #158·#345). 공유 상세 빨간 테두리·“바로 가능”도 같습니다. 예외는 물만.
- 공유 저장은 레시피 줄의 `categoryCode`를 공통 담기에 전달해요. 이름이 사전과 정확히 일치하면 사전 카테고리가 우선이고, 사전에 없어도 레시피에 확정 카테고리가 있으면 담아요. 담기 대상에 둘 다 없으면 `INVALID_INPUT`으로 저장·장바구니 변경을 모두 롤백하고 성공 이벤트도 남기지 않아요. 임의 `ETC` 지정이나 재료 건너뛰기는 하지 않아요([#245 합의](https://github.com/likelion-backendschool-9th/REMAKE/issues/245#issuecomment-7182102063)).
- #277 이전 레시피와 AI가 유효한 카테고리를 주지 않은 줄은 `categoryCode`가 비어 있을 수 있어요. 사전에도 없는 부족 재료라면 공유 저장 실패가 남아요. 기존 데이터는 이 작업에서 다시 분류하지 않으며, 내 레시피 저장의 누락 재료 건너뛰기와 공유 저장의 전체 실패를 통일할지는 별도 후속으로 검토해요.
- 저장 취소는 원본의 내 저장만 삭제하고 장바구니를 유지해요. 반복 취소도 성공해요. 취소 후 재저장은 현재 부족한 재료 중 기존 장바구니에 없는 행만 추가하고 사용자가 수정한 수량과 최초 슬롯 출처를 보존해요.
- 신규 저장과 장바구니 담기는 같은 트랜잭션이에요. 실패하면 저장·장바구니가 함께 롤백되고 성공 이벤트도 남지 않아요. E44 `recipe_saved`는 `save_source=shared`, `cart_added_count`에 실제 추가 행 수를 기록해요. 내 레시피 저장 E44는 `own`을 사용하고, 클라이언트 E45도 저장 출처에 맞는 `own` 또는 `shared`만 허용해요. E62는 공통 담기만 발행하며 `shared_recipe_saved`는 사용하지 않아요.

## 조리 사진 저장 (#64)

- [#174 최종 결정](https://github.com/likelion-backendschool-9th/REMAKE/issues/174)에 따라 서버는 사진 1장 필수·최대 5MiB(5,242,880바이트, 경계값 포함)·JPEG/PNG/WebP를 받아요. #155의 서버 구현 규격을 최종 기준으로 채택하며 기존 기획의 공유 사진 10MB·JPG/PNG/HEIC 기준을 대체해요. 영수증은 기존 10MB·jpg/png/heic를 유지해요. 누락·빈 파일은 `PHOTO_REQUIRED`, MIME·헤더 불일치는 `UNSUPPORTED_FILE_TYPE`, 용량 초과는 `FILE_TOO_LARGE`예요. 신고된 크기뿐 아니라 실제 스트림 길이도 검사하고, 서버에서 이미지 전체 디코딩·변환까지 하지는 않아요.
- HEIC 사진 입력은 FE에서 JPEG 또는 WebP로 변환해 지원해요. 원본 HEIC를 서버에 보내지 않으며, 변환 결과도 허용 형식·5MiB 이하인지 확인해요. 변환 실패나 처리 후 용량 초과 시 업로드를 막고 다른 사진 선택을 안내해요. 일반 사진 축소·압축과 HEIC 변환은 구분해 검증해요. 긴 변 2000px·품질 80%는 시작값 제안이며 확정 규격이 아니에요.
- 사진 선택·미리보기·축소·압축·HEIC 변환은 #329, 처리한 파일의 multipart 전송·응답/오류 처리는 #112에서 구현해요. #329 PR에 지원 환경·출력 형식·용량 경계·실패 안내 검증을 남겨야 해요. 정책 확정과 FE 구현 완료는 구분하며, 현재 HEIC 변환·브라우저 호환성 검증이 끝난 것으로 표시하지 않아요.
- `StoreSharedRecipePhotoUseCase.store(SharedRecipePhotoUpload)`는 사진 1장을 저장하고 임의 `imageKey`를 반환해요. #86 게시 UseCase가 쓰기 트랜잭션을 시작하고 같은 트랜잭션에서 `shared_recipes.image_key`에 저장해야 해요. 별도 사진 테이블은 만들지 않아요.
- 저장 경로는 `remake.upload.root-directory`이며 `REMAKE_UPLOAD_ROOT_DIRECTORY`와 명시적으로 연결해요. 로컬 기본값은 `${java.io.tmpdir}/remake-uploads`, 운영은 환경변수가 필수이고 공용 볼륨 `/data/uploads`를 사용해요. 운영에서 임시 폴더로 대체하지 않아요. 배포 담당자가 별도 PR로 볼륨·compose 변수·Nginx 제한을 추가하므로 기능 머지 전에 반영을 확인해요.
- `FileSystemSharedRecipePhotoStorageAdapter`는 `shared-recipes/` 아래에 저장하고 기존 키를 덮어쓰지 않아요. 잘못된 경로·심볼릭 링크 읽기를 거절해요. `LoadSharedRecipePhotoPort`는 스트림·MIME·길이를 반환하며 호출자가 스트림을 닫아야 해요. 없는 파일은 빈 결과이고, 이미 없는 파일 삭제는 성공해요.
- 저장 실패 때 시도한 파일을 정리하고 트랜잭션 롤백 때 새 파일을 삭제해요. 즉시 삭제 실패는 롤백 때 재시도하며, 계속 실패하면 외부 오류 원문 없이 경고를 남기고 운영 정리가 필요해요. 프로세스 중단 복구까지 보장하지는 않아요. 사진 처리 자체에서는 이벤트를 발행하지 않아요.
- Spring 제한은 영수증과 공존하도록 파일당 10MB·요청 전체 30MB이고 공유 서비스가 별도로 5MiB를 검사해요. 두 Nginx의 32m 제한은 배포 담당자 작업이에요.
- #86에서 게시·DB 연결과 로그인 및 공유 글 공개 상태를 확인하는 사진 API를 구현해요. 요청에서 임의 파일 경로를 받거나 볼륨을 공개 정적 폴더로 열지 않아요. 내 공유 글 삭제 API는 아직 없고(미결), 탈퇴하면 작성자가 지우지 않은 공유 글과 사진만 익명으로 유지하므로 영수증 이미지와 함께 삭제하지 않아요. FE 사진 전처리와 인증 이미지 표시 컴포넌트는 #329, 실제 API 및 인증 이미지 URL 연결은 #112 범위예요.

## 영수증 연동 계약(#57)

2026-11-24 담당자 합의 기준이에요. 차감 UseCase 구현과 영수증 API·화면 연결은 별도 작업이에요.

```java
// com.remake.cart.application.port.in
public interface DeductCartItemsUseCase {
    int deduct(Long userId, List<CartDeductionCommand> deductions);
}

public record CartDeductionCommand(
    Long cartItemId,
    String ingredientName,
    BigDecimal amount,
    IngredientUnit unit
) {}
```

- 영수증 요청의 품목마다 `cartDeductions: [{ cartItemId, amount }]`를 받아요. 생략·빈 배열은 차감 없음이며, 첫 버전은 품목당 대상 행 0~1개예요. 차감 수량을 1로 제한하는 뜻은 아니에요.
- 영수증 쪽은 대상 개수, 양수 차감량, 품목별 실제 냉장고 등록량 이하인지를 먼저 검증해요. 최종 등록에 사용하는 재료명·서버 결정 `IngredientUnit`으로 명령을 만들어 같은 트랜잭션에서 호출해요.
- 장바구니 쪽은 소유자·정확히 일치하는 이름·동일 단위를 검증해요. 여러 품목이 같은 `cartItemId`를 선택하면 모두 검증한 뒤 차감량을 합산해 현재 잔량과 비교해요. 단위 환산은 하지 않아요.
- 반환 `int`는 `cartRemovedCount`, 즉 잔량이 0이 되어 실제 삭제된 행 수예요. 5개에서 2개를 빼면 0, 2개에서 2개를 빼면 1이에요. 같은 행을 여러 품목이 차감해도 삭제수는 1이에요.
- 미선택은 호출을 생략하고 0을 사용해요. 빈 목록을 호출해도 0이에요.
- 없는 항목·타인 항목은 404 `CART_ITEM_NOT_FOUND`, 이름·단위·수량 오류는 400 `INVALID_INPUT`, 대상별 합계가 잔량을 초과하면 400 `INSUFFICIENT_QUANTITY`와 `details.remaining`이에요.
- 호출자의 영수증·냉장고 등록 트랜잭션에 참여해요. 검증·저장 실패는 예외로 전달하고 전체 등록을 롤백해요. 행을 ID 오름차순으로 잠가 동시 요청도 최신 잔량을 검증하게 해요.
- 영수증 차감 UseCase와 저장 기반은 #218/#219에서 구현했어요. #89는 공통 담기·조회·수량 변경·선택 삭제·냉장고 이동 API를 구현해요. 영수증 실제 호출은 #49, 레시피 저장 호출은 #76/#90, 식단 연동(생성·칸 교체 담기, 칸 삭제·교체·덮어쓰기 정리)은 #91에서 연결해요.
- 공통 담기는 사용자+원본 recipeId+정확히 일치하는 재료명+단위로 중복을 판별하고 기존 행의 수량·최초 슬롯 출처를 유지하는 기준으로 진행해요. 이는 사용자 승인 기준이며, #89에서 DB 중복 키와 원자적 insert로 동시 담기를 방지해요.

## 공통 담기 호출 계약(#89)

```java
int added = addCartItemsUseCase.add(userId, source, commands);
// CartSource: OWN_RECIPE / SHARED_RECIPE / MEAL_PLAN
// CartAdditionCommand: recipeId, mealPlanSlotId, ingredientName, amount, unit, categoryCode
```

- 원본 recipeId는 모든 출처에서 필수예요. 호출자는 원본·슬롯의 접근 권한과 연결 관계를 검증하고 최종 냉장고 부족 재료 목록만 전달해요. 공통 담기에서 냉장고 부족분을 다시 계산하지 않아요. 수동 담기 API는 없어요.
- mealPlanSlotId는 식단표 출처에서만 전달해요. MEAL_PLAN은 이번 호출의 같은 키를 먼저 합산하고 최초로 전달한 슬롯 출처를 사용해요. 나머지 출처의 중복 키는 첫 항목을 유지해요. 기존 장바구니 행의 수량·슬롯은 모두 보존해요.
- 이름은 앞뒤 공백을 정리한 뒤 정확히 비교하고, 단위가 다르면 합치지 않아요. null 수량·PINCH·TO_TASTE·물은 담지 않아요. 카테고리는 사전 정확 일치가 우선이며 없으면 호출자가 넘긴 서버 확정 categoryCode가 필요해요.
- 반환값과 E62 `item_count`는 실제 추가한 행 수예요. 0행은 이벤트를 발행하지 않아요. E62 `cart_source`는 `own_recipe`·`shared_recipe`·`meal_plan`으로 발행해요.
- `V18__prevent_duplicate_cart_additions.sql`이 원본 recipeId가 있는 행에 사용자·레시피·이름·단위 유니크 인덱스를 추가해요. 이미 병합된 마이그레이션은 수정하지 않아요. #224의 영수증 테이블 V17과 겹치지 않도록 이 PR에서 V18로 조정했어요. #224(V17)을 먼저 병합·적용하는 순서가 기준이에요. 순서가 바뀌거나 다른 PR이 번호를 먼저 쓰면 후순위 PR의 번호를 다시 조정해요.

### #92 주간 확정·보상 구현

- `FinalizeWeeklyRankingUseCase.finalizePreviousWeek()`가 직전 KST 주를 확정해요. 스케줄러는 월요일 00:00에 호출하며 테스트·시연도 같은 내부 UseCase를 사용해요. 관리자 실행 API는 추가하지 않아요.
- 공개 글에 대해 지난주 월요일 00:00 이상·이번 월요일 00:00 미만에 저장했고 현재 남아 있는 행만 세요. 저장 0건 제외는 확정이고, 본인 저장 제외·동점은 먼저 공유한 글 우선(ID로 최종 정렬)은 #88과 같은 제안이에요.
- 주별 완료 기록·최대 100위·보상을 한 트랜잭션으로 저장해요. 빈 주도 완료 기록이 남고, 동시 실행·재실행은 중복 지급하지 않아요. 중간 실패는 모두 롤백하여 다시 시도할 수 있어요.
- 상위 3개 레시피마다 +10/+6/+3회를 주고 같은 작성자의 중복 수상도 허용해요. 탈퇴자는 순위에 남기되 보상을 건너뛰고 차순위에 넘기지 않는 것은 제안이에요.
- 만료는 실제 지급 시각 + 1개월(해당 일이 없으면 월말)이에요. 남은 횟수 조회와 생성 차감에 연결하며, 기본 횟수를 먼저 쓰고 보상은 만료가 가까운 것부터 사용해요. 만료 시각부터 사용할 수 없어요.
- E75는 실제 보상 건마다 커밋 후 EventTracker로 발행해요. 이벤트 적재 실패는 보상 지급을 취소하지 않으며 재실행으로 재전송하지 않아요.
- 한계: 저장 취소 이력이 없어 첫 실행이 늦으면 주 경계 이후 취소된 저장을 복원할 수 없어요. 실행 시점의 남은 저장을 세며 누락 주 자동 소급 실행은 제공하지 않아요. #230의 작성자 삭제·확정 후 보상 정책은 미결로 남겨요.
